npm i -g claudekishmish

claudekishmish

Keep a Claude Code usage window always running — and continue interrupted work in the terminal it stopped in.

v0.3.0 Windows · macOS · Linux MIT 1 dependency
The problem

A window you never claimed is time you never get back

A Claude Code usage window is five hours long. It starts at your first message — and it only advances when someone claims it. If your window ends at 02:00 and you send nothing until 09:00, those seven hours were dead. No window was running, so nothing accrued to you.

Install · about two minutes

Three steps, then never think about it again

  1. Install the package

    terminal
    $ npm i -g claudekishmish

  claudekishmish
  Credits to Gantavya Singh Shekhawat

  Next:  ckm setup

  2. Run setup

    This writes the shim and the background service, then prints the one thing left for you to do.

    terminal
    $ ckm setup

  Two steps left — run these yourself:

  1. Put the shim FIRST on PATH —
     run it once, then open a new terminal:

     [Environment]::SetEnvironmentVariable('Path', ...)

  2. Start the background claimer.

  Both jobs are ON:
    auto-continue   ON   continue interrupted work
    window claiming ON   keep the countdown running

  3. Run the PATH line, then open a new terminal

    Not optional. Until the shim is on PATH, only half the tool is running: boundaries get claimed, but nothing is watching your sessions, so nothing can continue your work.

    On Windows, use the persistent line setup prints. The obvious $env:Path = … form lasts only until you close the terminal — and a tool that stopped working looks exactly like a tool that is working.

That's it. From here, run claude exactly as you always have.

What it does

Two jobs, both on by default

Job one

Claims the boundary

The moment a window expires, a minimal request starts the next countdown — even with no terminal open and nobody awake. Capped at 14 a week, announced at setup, and every claim is logged before it happens.

Job two

Continues your work

When a session stops at a limit, the continuation is typed into your actual terminal session once the window reopens. Same window, same context, work carries on.

Three limits, three responses

Not every limit is the same limit

Claude Code has three separate caps, and treating them as one is what makes naive wait-and-retry tools hang for days. This is the panel they come from — /usage inside Claude Code:

LimitWhat claudekishmish does
Session
every 5 hours		Waits for the stated reset, then continues your work.
WeeklyParks it, suspends claiming so it can't spend the budget it exists to protect, and tells you.
Per-modelStops cleanly and hands back. Waiting cannot clear this one, so it doesn't pretend otherwise.
API overloaded
529 · stalled · dropped		No reset time exists, so it retries on a bounded backoff — 30s, 1m, 2m, 4m, 8m, then stops.

And if the account itself can't make requests — logged out, subscription ended — it halts rather than retrying an impossible request several times a day forever.

Worth knowing

What it will not do

It does not reset, extend or bypass server-side limits — that's impossible, and nothing here attempts it. It waits for normal availability and then makes ordinary requests on your own account.

A sleeping machine claims nothing. If your laptop is suspended at 02:00, that boundary is claimed when you wake it, not at 02:00. Nothing in user space can fix that; if you want the countdown to survive the night, the machine has to stay awake.

And it never types over a message you've half-written. Every keystroke is forwarded, so it knows when your input box has a draft in it — appending to that and pressing Enter for you is the one way a tool like this could destroy work instead of saving it.
